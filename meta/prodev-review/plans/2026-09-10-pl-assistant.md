# 과제 비서 — minidiscord 위에서 과제 하나를 처음부터 끝까지 (기획 초안, 2026-09-10)

이 글은 crew 실험 다섯 회차와 고영혁 팀 분석(`notes/external-evidence-gonnector.md`) 뒤에 사람이 낸 물음에 답한다.
**"방을 만들고 봇을 초대해, 과제 발의부터 보고서까지 minidiscord 안에서 쭉 하고, 나는 모두를 다 아는 봇과 일한다고 느껴야 한다."**

---

## 0. 한 줄 결론

> **두뇌는 하나, 사람은 여럿, 봇은 일의 길이만큼.**

고영혁 팀은 사람 하나에 봇 열둘이다. 우리는 반대다. PL 과 과제원 여럿이 사내망에서 같은 방에 들어온다. **minidiscord 의 진짜 장점은 봇을 여럿 두는 것이 아니라 사람을 여럿 들이는 것**이다. 그래서 "모두를 다 아는 봇"은 이름 하나, 기억 하나여야 한다. 봇이 여럿이면 기억이 갈라지고, 회차 4 에서 본 것처럼 계층을 넘으며 사실이 떨어진다.

봇 수에 제한은 두지 않되 기준을 둔다. **과제마다 상주하는 비서 하나**. 리서치·특허·논문·보고 같은 일은 비서 안의 스킬(서브에이전트)로 시작하고, 그 일이 **며칠을 이어지며 사람이 그 일 담당과 직접 말하고 싶어질 때** 별도 봇으로 떼어 낸다. 떼어 낸 봇도 같은 지식 저장소를 읽고 쓴다. 지식은 봇에 있지 않고 폴더에 있다.

## 1. 무엇이 있고 무엇이 없나 (minidiscord 2026-09-10 실측)

| 있다 | 기획에서 어떻게 쓰나 |
|---|---|
| 방 만들기 · 보관(읽기 전용) | 과제 하나 = 방 묶음. 일이 끝나면 보관. 보관된 방도 이력 조회는 된다 |
| `@TO` / `@CC` 봉투 | TO 만 답한다. CC 는 읽고 기억한다 |
| 사람 첨부 → 봇에게 **로컬 경로**로 전달 | 과제원이 올린 파일·캡처를 봇이 그 자리에서 연다. 이미지는 Claude 가 직접 본다 |
| 봇 첨부 (`MINIDISCORD_BOT_FILES_DIR`) | 봇이 그림·표·자른 이미지를 방에 올린다. "이 부분이 무엇입니까"를 그림으로 묻는다 |
| `fetch_history` (커서 · 발화자 · 날짜) | 놓친 대화 따라잡기. 방 × 봇 책갈피가 서버에 있어 봇이 꺼졌다 켜져도 이어진다 |
| 권한 승인이 방으로 옴 | 위험한 명령은 PL 이 방에서 승인. 승인 목록은 봇 설정에 |
| HTTP API (`POST /api/rooms/:id/messages`) | 바깥에서 봇을 깨울 수 있다. **cron + curl 로 아침 브리핑**이 서버 수정 없이 된다 |
| 봇 글 6개 연속이면 TO → cc | 되돌이 차단. 비서 하나면 거의 안 걸린다 |

| 없다 | 필요한가 | 어디서 고치나 |
|---|---|---|
| **대화 전문 검색** | **필수.** "그때 뭐라 했지"가 이 기획의 절반이다 | minidiscord 저장소 (SQLite FTS5 + 웹 검색창 + 봇 도구 `search_history`) |
| 이력 조회의 `limit` 이 `since_id` 보다 먼저 걸림 (OD-9) | 필수. 자료 방에 글이 밀리면 앞을 영구히 놓친다 | minidiscord 저장소 |
| 스레드 · 답장 대상 | 있으면 좋다. 지금은 인용으로 대신한다 | 나중 |
| 예약 실행(tick) | cron + API 로 대신한다 | 서버 수정 불필요 |
| 방 묶음 표시 | 이름 접두어로 대신한다 (`수율개선/자료`) | 나중 |

규칙대로 minidiscord 수정은 그 저장소에서 세션을 따로 띄운다. 여기서는 무엇이 필요한지만 적는다.

## 2. 방의 구조 — 과제 하나는 방 묶음이다

```
수율개선-2026q3            본방. PL·과제원·비서. 발의·일정·일상 질문·결재
수율개선-2026q3/들이기     과제원이 파일을 올리고 비서와 묻고 답하는 방. 어지러워도 된다
수율개선-2026q3/자료       비서만 쓴다. 확정된 자료 한 건에 글 하나. 이 방 자체가 눈으로 훑는 색인이다
수율개선-2026q3/리서치     리서치 한 건에 방 하나가 아니라, 리서치 흐름 전체. 브리핑과 토론
수율개선-2026q3/특허       특허 조사·전략. 필요할 때 연다
수율개선-2026q3/논문       논문 와꾸·집필. 필요할 때 연다. 길어지면 논문 봇을 따로 둔다
수율개선-2026q3/보고       주간·월간·경영진 보고. 포맷 파일이 여기 올라온다
```

방을 나누는 까닭은 봇이 아니라 **사람의 편의**다. 과제원은 들이기 방만 보면 되고, PL 은 본방과 보고 방을 본다. 자료 방은 아무도 말하지 않는 방이라 스크롤만 해도 과제의 자료 목록이 된다.

봇의 폴더 대응: 방 이름의 `/` 를 `-` 로 바꾼 것이 지금 규칙이다. 비서는 접두어(`수율개선-2026q3`)로 과제를 알아내고, 과제 폴더 하나에 방마다 하위 폴더를 둔다.

```
rooms/수율개선-2026q3/
  charter.md          과제 헌장 (발의 대화의 결과)
  schedule.md         일정. 파일이 진실
  journal/2026-09-10.md   방마다·날마다 비서가 쓰는 일지 (결정·미해결·다음 할 일)
  inbox/              원본 (불변) + 사이드카 .md
  cards/              자료 카드 (한 건에 하나)
  wiki/               주제 페이지
  index.md            기계가 만든다. 손으로 안 쓴다
  research/ patent/ paper/ report/   일 갈래별 산출물
  handoff.md          비서의 지금 상태 (6줄)
```

## 3. 봇 — 비서 하나와 떼어 내는 규칙

### 비서 (상주, 과제마다 하나)

| | |
|---|---|
| 이름 | 과제 이름을 딴 기능명. 캐릭터 이름은 근거가 없어 안 쓴다 |
| 들어가는 방 | 그 과제의 방 전부 |
| 하는 일 | 발의 대화 · 들이기 문답 · 찾기와 답하기 · 일정 · 일지 · 리서치·보고의 1차 |
| 안 하는 일 | 스스로 새 일을 만들지 않는다. 리서치 시작 · 자료 확정 · 보고서 발송은 사람의 한마디가 있어야 한다 |
| 기억 | 파일뿐. 깨어날 때 훅이 charter · schedule · handoff · 오늘과 어제 일지 · index 머리 30줄을 실어 준다 |

### 떼어 내는 규칙 (봇을 늘리는 유일한 기준)

일이 **며칠 이어지고**, 그 일의 담당과 **사람이 직접 대화하고 싶고**, 그 대화가 **본방의 일상과 섞이면 불편할 때**. 논문 집필이 전형이다.
떼어 낸 봇은 같은 과제 폴더를 읽고 자기 갈래 폴더(`paper/`)에만 쓴다. 비서는 그 방에 CC 로 앉아 일지에 요약만 남긴다.
셋 이상 떼어 낼 일은 거의 없다. crew 의 다섯은 역할 표가 있어서 채운 것이지 일이 있어서가 아니었다.

### 스킬 (비서 안에서 불릴 때만 문맥에 온다)

| 스킬 | 언제 | 무엇을 남기나 |
|---|---|---|
| `charter` | "과제 발의하자" | `charter.md` — 목적 · 목표 · 일정 · 인원 · 예산 · 판정 기준 |
| `intake` | 들이기 방에 파일이 올라오면 | 문답 → 사이드카 → 카드 → 자료 방 글 한 건 |
| `find` | 무엇이든 물으면 | 정해진 순서로 찾고 출처를 단 답 |
| `research` | 사람이 허락하면 | `research/<주제>.md` + 브리핑 + 카드 |
| `schedule` | 일정 말이 나오면 | `schedule.md` 갱신 + 브리핑 |
| `patent` · `paper` · `report` | 사람이 열면 | 갈래 폴더 산출물 |
| `journal` | 하루 끝 또는 압축 직전 | `journal/날짜.md` |
| `close` | 갈래가 끝나면 | 방 보관 · knowledge 승격 후보 목록 |

훅으로 가는 것: 분량 세기(count.js 그대로), 커밋 경로 고정, 자료 확정 전 사람 확인 문구가 있었는지 검사, 발송 전 결재 검사. **세는 것과 막는 것은 기계, 정하는 것은 지침.**

## 4. 시나리오 일곱 — 각각 어떻게 도나

사람이 적어 준 순서 그대로다. 표 하나에 방 · 시작 · 봇이 하는 것 · 남는 것 · 사람이 정하는 지점.

|---|---|---|---|---|---|---|
| 1 | 과제 발의 | 본방 | PL 이 "과제 하나 발의하자" | 목적·목표·일정·인원·예산을 **하나씩** 묻는다. 한 번에 다 묻지 않는다. 다 모이면 헌장 초안을 올리고 빈 칸을 표시한다 | `charter.md`, `schedule.md` 의 마일스톤 뼈대, 방 묶음 생성 | 헌장 결재 |

## 5. 두 번째 두뇌 — llm-wiki 인가 index 인가

**둘 다이고, 층이 다르며, 만드는 주체가 다르다.**

```
층 0  원본 + 사이드카        대화가 만든다      불변. 들이기 문답의 결과가 사이드카에 남는다
층 1  카드 (자료 한 건 = 파일 하나)   대화가 만든다      요약 · 조건 · 수치 · 관련 카드 링크 · 태그
층 2  주제 페이지 (위키)      비서가 쓴다        "지금 우리가 아는 것 / 근거 카드 / 모르는 것 / 바뀐 이력"
색인  index.md              기계가 만든다      카드·위키·원본의 머리말을 긁어 표로. 손으로 안 쓴다
대화  minidiscord DB         서버가 만든다      전문 검색 (FTS5) 이 붙어야 한다
```

crew 실측에서 **위키는 아무도 안 읽었다.** 까닭은 읽을 이유가 없어서였다. 봇끼리 파일 경로로 넘겼으니 위키를 거칠 일이 없었다.
이 기획에서는 읽는 이유가 생긴다. **사람이 묻고 비서가 답한다.** 그 답의 출처가 위키와 카드다.

그래도 같은 함정을 피하려면 둘을 지킨다.

1. **찾기 순서를 스킬에 못 박는다.** `index.md` → 카드 머리말 grep → 위키 → 대화 검색 → 원본. 한 단계에서 찾으면 멈춘다. 답에는 어느 층에서 찾았는지 경로를 단다.
2. **위키는 카드가 들어올 때만 고친다.** 카드 없이 위키만 자라면 근거 없는 문장이 생긴다. 위키의 모든 문장은 카드 하나를 가리킨다.

그리고 잰다. **찾기 성공률**이 이 층 구조가 값을 하는지의 지표다. 사람이 물은 것 중 비서가 카드나 위키를 출처로 답한 비율. 대화 검색으로만 찾은 비율이 높으면 카드가 일을 안 하는 것이다.

카드 머리말은 crew 의 규격을 그대로 쓴다 (`kind · title · created · aliases · tags · sources · status · supersedes`). 여기에 둘을 더한다. `who`(올린 과제원) 와 `confirmed_at`(문답이 끝난 message_id). 이 둘이 있어야 "이 자료 누가 언제 확정했지"가 대화까지 되짚어진다.

## 6. "모두를 다 아는 봇"이 되는 장치 — 기억은 파일, 이어짐은 훅

봇 세션은 압축되고 꺼진다. 그래도 사람이 그것을 못 느끼게 하는 장치는 넷이다.

| 장치 | 무엇 | 언제 |
|---|---|---|
| 서버 책갈피 | 방 × 봇의 `last_delivered_id`. 놓친 TO 는 재접속 때 다시 온다 | 이미 있다 |
| session-start 훅 | charter · schedule · handoff · 오늘과 어제 일지 · index 머리 30줄을 문맥에 싣는다 | 시작 · 재개 · clear · 압축 뒤. crew 의 `session-start.js` 를 거의 그대로 |
| 일지 | 방마다 하루 하나. 결정 · 미해결 · 다음 할 일 · 누가 무엇을 올렸나. 한 줄씩 | 하루 끝 (cron 이 깨움) 과 압축 직전 (PreCompact 훅) |
| handoff | 지금 하고 있던 것 6줄. "들이기 방 message 412 의 문답 중, 남은 질문 하나" | 행동 전에 저장, 행동 뒤에 갱신 |

고영혁의 "일기"와 겹치지만 목적이 다르다. 그의 일기는 봇의 소회이고 지혜 승격은 계측이 없다. 여기의 일지는 **다음 세션이 읽을 사실**만 적는다. 감상은 안 쓴다.

압축이 일어난 뒤 비서의 첫 일은 handoff 를 읽고 "이어서 하겠습니다. 남은 질문은 이것입니다"라고 방에 한 줄 쓰는 것이다. 사람은 그 한 줄로 끊김을 못 느낀다.

## 7. 사람의 자리 — 셋 중 하나만 한다

## 10. 지침의 뼈대 (비서 CLAUDE.md, 60줄 안쪽을 겨눈다)

정하는 것만 남긴다. 절차는 스킬, 세는 것은 훅.

- 나는 과제 `<이름>` 의 비서다. 이 과제의 방 전부에 있다. 방 이름의 접두어가 내 과제 폴더다.
- 봉투만 믿는다. TO 에 답하고 CC 는 읽는다. 사람에게는 이름만 부르고 멘션을 안 붙인다.
- 답하기 전에 찾는다 (`find`). 출처 없는 사실은 말하지 않는다. 모르면 모른다고 한다.
- 스스로 일을 만들지 않는다. 리서치·갈래 방은 사람이 허락해야 연다.
- 자료는 과제원이 "맞다"고 해야 확정이다. 확정 전에는 자료 방에 쓰지 않는다.
- 파일이 진실이다. 행동 전에 handoff 를 쓴다. 하루 끝과 압축 전에 일지를 쓴다.
- 사람에게 하는 말은 900자 · 10줄 안. 넘치면 파일로 옮기고 경로를 준다. 세는 것은 훅이 한다.
- 한 번에 묻는 것은 셋까지. 그림으로 물을 수 있으면 그림으로 묻는다.
- 내 폴더에만 쓴다. 원본은 손대지 않는다. 지우지 않고 void 로 바꾼다.

crew 공통 지침 183줄 가운데 여기 오는 것은 열 줄 남짓이다. 나머지는 봇 다섯의 조율 규칙이었고, 비서 하나에는 필요 없다.

## 13. 기능 1 — 대화는 무제한이다. fetch_history 가 아니라 DB 를 직접 본다

**확인됨**
- 봉투에 `message_id` 가 온다. 봇은 "지금 몇 번째 줄인지" 를 언제나 안다.
- 메시지 번호는 서버 전체 하나의 autoincrement 다 (방마다가 아니다). 방 안에서는 단조 증가하므로 `since` 가 성립한다.
- `node:sqlite` 를 `readOnly` 로 열어 서버가 켜진 채로 읽힌다. 시제품 `plans/proto/chat.js` 로 여섯 명령을 사본에서 시험했다: `rooms` · `search <말> [--room --speaker --since --until --limit --full]` · `around <id>` · `since <방> <id>` · `tail <방> N` · `show <id>`(본문 전문 + 첨부의 실제 경로).
- SQLite 3.50 에 FTS5 trigram 이 있다. 지금은 LIKE 로 충분하다 (377건 즉시). 수만 건이 되면 FTS 로 옮긴다.

**설계**
- 비서는 `fetch_history` 를 쓰지 않는다. 깨어나면 `since <방> <handoff 의 마지막 id>` 로 따라잡고, 물음이 오면 `search` 를 먼저 돌린다.
- 찾기 순서(5절)의 "대화 검색" 층이 이것이다. 카드에 없고 대화에만 있는 사실은 답에 `#id` 를 단다. 사람이 그 번호로 되돌아갈 수 있다.
- `show` 가 첨부의 실제 경로를 돌려주므로, 옛 파일도 대화 번호로 되찾아 다시 연다.
- 웹 화면의 검색창은 사람 편의다. 봇에게는 급하지 않으므로 minidiscord 수정 순서에서 뒤로 보낸다. OD-9(이력 조회 순서)는 봇이 `fetch_history` 를 안 쓰면 봇에게는 문제가 아니다.

**남은 물음**
- 검색어가 여럿일 때 AND 로 볼지, 가까운 순으로 볼지. 지금은 한 덩어리 부분 일치다.
- 봇이 방 전체를 훑는 값. `search --limit 50` 한 번이 문맥 약 2~4K 토큰이다. 하루 몇 번이면 무시할 만하다.

## 14. 기능 2 — 오토컴팩트를 켜 두고, 압축 직전에 인수인계서를 만든다

**확인됨** (Claude Code 훅 문서 + 이 세션의 실행)
- `PreCompact` 는 stdin 으로 `transcript_path · session_id · cwd · compaction_trigger(auto|manual)` 를 받는다. **문맥을 넣을 수는 없다.** 시간은 넉넉하다 (기본 600초, `timeout` 으로 조정).
- 넣는 자리는 `SessionStart` 의 `compact` 경우이고 `additionalContext` 로 넣는다. crew 의 `session-start.js` 가 이미 이 자리에 걸려 있다. `PostCompact` 도 있지만 넣지 못한다. 사람이 인용한 글의 "직후 훅에서는 못 넣는다" 가 이것이다.
- 훅 안에서 `claude -p` 가 돈다. 이 세션에서 haiku 로 실측: 7초, $0.02.
- 대화 기록 파일(JSONL)은 `type: user|assistant` 줄의 `message.content` 가 글이거나 블록 배열(text · tool_use · tool_result · thinking)이다. 꼬리 N 턴을 읽는 데 충분하다.

**설계**
1. `PreCompact` 훅: 기록 파일의 꼬리에서 최근 턴을 모은다 (tool_result 는 앞 300자, thinking 은 뺀다). 고정 서식의 인수인계서를 `claude -p --model sonnet` 로 만든다.
   ```
   하던 일: (함수·파일·메시지 번호 단위로)
   방과 마지막 message_id:
   사람이 기다리는 것:
   미해결 질문:
   다음 한 걸음:
   열어 둔 파일:
   ```
   `bots/<비서>/handoff-compact.md` 에 덮어쓰고 `journal/<날짜>.md` 에 한 줄 덧붙인다. 실패해도 세션을 막지 않는다 (fail-open).
2. `SessionStart(compact)`: `handoff-compact.md` 를 맨 앞에 싣고, 그 뒤 charter · schedule · handoff · 일지 순서. 비서의 첫 일은 방에 "이어서 합니다. 남은 것은 …" 한 줄이다.
3. 행동 전 `handoff.md` 저장(crew 규칙)은 그대로 둔다. 인수인계서는 둘째 안전망이다. 둘 다 있어야 함수 이름 단위로 잡힌다.
4. **압축 진행 표시**: 훅이 minidiscord HTTP API 로 방에 "비서가 문맥을 정리하는 중입니다 (약 1분)" 를 올린다. 봇 이름으로는 못 올리므로(봇 글은 게이트웨이만 보낸다) 알림용 사람 계정 하나를 둔다. 끝나면 비서 자신이 "이어서 합니다" 로 닫는다.

**사람이 인용한 글의 경고와 우리의 관계**
- "미리 백업하면 뒤 기록이 통째로 빠진다" 는 그 사람의 기록 저장 장치의 중복 방지 때문이다. 우리는 기록 파일을 따로 저장하지 않는다. **대화의 원본은 minidiscord DB** 이고 압축과 무관하게 남는다. 그러므로 이 경고는 우리에게 해당하지 않는다.
- 45초의 값은 문맥 하나(비서)에 하루 몇 번이다. 무시할 만하다.

**남은 물음**
- 인수인계서 모델: sonnet(품질) 인가 haiku(속도) 인가. 함수 이름 단위가 목표라면 sonnet 이다.
- `autoCompactWindow` 를 어디에 둘지. crew 는 65만에서 세 세대 0회였다. 비서는 하루 종일 살아 있으므로 실제로 걸린다. 첫 값은 기본으로 두고 실측한다.
